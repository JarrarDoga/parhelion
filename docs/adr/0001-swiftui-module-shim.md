# 0001: Provide a `SwiftUI` module on Linux

- **Status:** Accepted
- **Date:** 2026-10-19

## Context

Parhelion exists so that one app codebase can build for iOS and also run on Linux. iOS app source
files begin with `import SwiftUI`. If Parhelion were importable only as `ParhelionUI`, every file would
need conditional imports:

```swift
#if canImport(SwiftUI)
import SwiftUI
#else
import ParhelionUI
#endif
```

That boilerplate spreads through the codebase, breaks code generated by templates and tools,
and is a step that a person or an agent can forget.

## Decision

Parhelion's package declares a target named `SwiftUI` whose only content is
`@_exported import ParhelionUI`. The target and its product exist only when the package manifest is
evaluated on Linux (`#if os(Linux)` in `Package.swift`).

Apps depend on the product with a platform condition:

```swift
.product(name: "SwiftUI", package: "parhelion", condition: .when(platforms: [.linux]))
```

## Consequences

- Unmodified SwiftUI sources compile on Linux. The `SourceCompatibilityTests` target verifies
  this with a file that imports `SwiftUI`, not `ParhelionUI`.
- The same package builds for iOS. We verified this on 2026-10-19: an app with the dependency
  above built for iOS with xtool 1.22.2, and the resulting binary linked
  `/System/Library/Frameworks/SwiftUI.framework` and contained no reference to `ParhelionUI`.
- Parhelion cannot provide the `SwiftUI` module on macOS, because Apple's framework has that name.
  On macOS, developers import `ParhelionUI` directly. This is acceptable because Parhelion targets
  Linux, and macOS already has Apple's SwiftUI.
- `@_exported` is an underscored attribute. Its behavior has been stable for many Swift
  releases, and widely used packages depend on it. If it changes, the shim is one file.
- Because the module is named `SwiftUI`, a reader can mistake an error on Linux for one from
  Apple's framework. Compiler diagnostics name the declaring module, `ParhelionUI`, which shows
  where a type comes from.
